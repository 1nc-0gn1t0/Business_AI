# BA-011: каталог банковских продуктов и подбор

Модуль `apps/api/app/bank`: `schemas.py`, `catalogue.json`, `matching.py`;
маршруты — `app/api/bank.py`, решение — [ADR-0007](adr/ADR-0007-bank-catalogue-matching.md).
На frontend добавлен раздел «Продукты ВТБ»; чат, карта и финансовые API сохранены.

## Исходные сведения и статус проверки

**Все шесть начальных карточек демонстрационные.** 23.10.2026 просмотрены
индексированные копии официальных публичных страниц ВТБ:

| Категория | Официальный источник |
| --- | --- |
| РКО | https://www.vtb.ru/malyj-biznes/ru/rko/ |
| Регистрация бизнеса | https://www.vtb.ru/malyj-biznes/registraciya/ |
| Торговый эквайринг | https://www.vtb.ru/malyj-biznes/acquiring/ |
| Интернет-эквайринг | https://www.vtb.ru/malyj-biznes/acquiring/internet-acquiring/ |
| Дебетовая бизнес-карта | https://www.vtb.ru/malyj-biznes/biznes-karty/ |
| Финансирование: справочный раздел | https://www.vtb.ru/malyj-biznes/kredity-i-garantii/ |

Назначение продуктов описано кратко, без копирования тарифов, акций, ставок,
комиссий, сроков или обещаний открытия/одобрения. Кредитная бизнес-карта не
подставляется вместо дебетовой; финансирование не является конкретным кредитом.

Прямой web-fetch возвращал 502; Python urllib и PowerShell Invoke-WebRequest
с включённой проверкой TLS не смогли подтвердить цепочку сертификатов.
Это ограничение проверки в нашей среде, а не доказательство недоступности банка.
Системное доверенное хранилище/сертификаты не менялись, TLS-проверка не отключалась.
Поисковая копия не доказывает актуальность условий на дату просмотра.

Поэтому `reviewed_at/last_reviewed_at=2026-10-23` — дата попытки проверки,
`verification=cached_only`, `last_verified_at=null`, `content_sha256=null`,
`mode=demonstration`, `status=unconfirmed`. Это видно в API и UI. Нет действующих
предложений в recommended_ids; демонстрационные результаты находятся отдельно.

## Версии и обновление

- Версия `vtb-demo-public-references-2026-10-23-v1`; срок пересмотра 30 дней.
- `Product`: стабильный id, версия, категория/назначение, статус, mode,
  last_reviewed_at, ссылки на sources, rules, applicable/unknown conditions, ограничения.
- `EvidenceSource`: официальный HTTPS URL ВТБ/vtbrussia (включая PDF), дата попытки,
  verification, дата прямой проверки/digest при наличии, summary/limitations.
- `EligibilityRule`: id, типизированное поле, one_of, объяснение, вопрос;
  origin=application_policy, purpose=relevance_only_not_bank_eligibility.
- Fingerprint каталога — SHA-256 канонического JSON; меняется при правке данных
  или правил. Версии нужно повышать явно, старые сохраняются в истории Git.
- Алгоритм `bank-relevance-three-valued-v1`; fingerprint запроса включает
  алгоритм, hash каталога, серверную UTC-дату as_of, профиль/его версию и needs.
  Один снимок и дата дают идентичный результат, порядок — product.id по возрастанию.

По умолчанию JSON поставляется внутри API image. Для редактирования без изменения
алгоритма обновите каталог, проверьте schema/tests и пересоберите API. Альтернатива —
локальный JSON через `BANK_CATALOGUE_PATH` в environment API и read-only volume
в Compose override. В `.env` сам по себе этот параметр в Compose не передаётся.
Файл перечитывается на запрос; публикуйте обновление атомарной заменой файла,
а не частичной записью. Повреждённый/отсутствующий JSON → 503, без fallback.

Перед переводом отдельной позиции в `public_reference/published` ответственный
должен открыть официальные источники с корректной TLS-проверкой, проверить назначение
и применимые условия, зафиксировать дату и SHA-256 просмотренного содержимого,
обновить unknown_conditions и review date. Источники должны быть verified.
Нельзя просто снять demo-флаг ради демонстрации действующих предложений.
Даже verified_reference — только публичная справка, не проверка клиента банком.

Даты из будущего и возраст проверки >30 дней блокируют запись. Retired/unavailable
и недоступный source блокируют её независимо от mode. Unconfirmed/cached_only
не допускаются в действующие рекомендации; лишь явный demonstration допускает
показ отдельного демо-совпадения. Истечение срока блокирует также demo.
Текущее as_of задаёт сервер, клиент не может подставить прошлую дату для обхода.

## Правила и неизвестные параметры

Все правила продукта объединены AND:

| Карточка | Явно требуемые потребности/состояния демо-политики |
| --- | --- |
| РКО | зарегистрированный ИП/юрлицо + нужен расчётный счёт |
| Регистрация | ещё не зарегистрирован + идея/подготовка + запрошена помощь |
| Торговый эквайринг | зарегистрирован + офлайн/оба канала + приём карт |
| Интернет-эквайринг | зарегистрирован + онлайн/оба канала + приём карт |
| Дебетовая бизнес-карта | зарегистрирован + явно нужна карта расходов |
| Справка о финансировании | явный интерес к информации |

Это открытые **правила приложения**, а не утверждение о полном соответствии
банковским условиям. Отрасль/MCC, сайт, документы, банковский счёт, региональная
доступность и тарифы остаются unknown_conditions, пока не проверены.

Неизвестное значение (`null`/отсутствует) → unknown, не true. Если есть явное
несовпадение → not_matched; иначе unknown → needs_clarification с вопросами;
все условия совпали → potential_match/information_only либо demo_match/demo_information.
Blocked → unavailable. Для неподтверждённого профиля решения не рассчитываются.

Город/бюджет/вид/формат из профиля сохраняются как контекст, не доказывают регистрацию
или канал продаж. «Кофейня/навынос» не превращается автоматически в офлайн-эквайринг.
Интерес к финансированию берётся из needs; только при отсутствии ответа loan/mixed
из подтверждённого профиля интерпретируется как интерес к справочной информации.
Явное «нет» в needs имеет приоритет. Trace сохраняет исходное значение funding
и интерпретированное bool, точный input_path, rule и origin=user_input.
Own_funds/undecided не считаются согласием на кредитные предложения.
OSM-score, банковская маржа, стиль речи, бюджет и финансовая прибыль не участвуют
в продвижении/скоринге. LLM не выбирает продукты и не вычисляет соответствие.

## API и гостевой доступ

- `GET /api/v1/bank-products`: публичный каталог, источники, доступность,
  версия/hash/as_of и причины блокировки. Нет пользовательских данных.
- `POST /api/v1/conversations/{id}/bank-products/matches`: защищённый read-only подбор.
  Заголовок X-Conversation-Token, тело `{expected_version, needs, catalogue_fingerprint?}`.
  Сервер читает настоящий профиль из PostgreSQL; профиль/confirmed из тела не принимаются.
- Неизвестный/чужой ключ → 404; нет ключа → 401; устаревшая версия профиля → 409;
  изменившийся hash каталога → 409 bank_catalogue_version_conflict; неверный DTO → 422;
  неисправный каталог → 503 bank_catalogue_unavailable.
- Результат: profile/needs snapshots, profile_version, decisions с rule evaluations,
  причинами и provenance, recommended_ids отдельно от demonstration_ids,
  missing_fields, версии/fingerprints/as_of, credit_decision=not_assessed.

Нет POST в банк, заявок, согласий или simulated receipts BA-012. Ключ не попадает
в URL/логи frontend/внешние ссылки. Подбор не меняет профиль, сообщения или историю.
Дополнительные потребности и результат живут в памяти вкладки; сбрасываются при
редактировании профиля/reload. Редактирование needs скрывает прежний результат.
Обновление каталога/даты или ошибка его загрузки также снимает старые решения.

## Пример кофейни

Казань, кофейня, 2 млн ₽, подтверждённый профиль со своими средствами:
без других ответов действующих рекомендаций и демо-совпадений нет — нужны уточнения.
После явного выбора «ИП», офлайн, приём карт, нужен счёт и дебетовая карта:
demo_match для РКО, торгового эквайринга и бизнес-карты; интернет-эквайринг не совпадает
по каналу; регистрация не подходит уже зарегистрированному бизнесу.
Финансирование при явном «нет» исключено. При unknown — спрашивается интерес;
при «да» — только demo_information, без ставки/лимита/оценки одобрения.
Для ещё не зарегистрированного бизнеса на стадии подготовки с запросом помощи
подходит только демонстрационная регистрационная карточка; РКО/карты/эквайринг
не выдаются как уже доступные до регистрации.

[Обезличенный детерминированный пример](examples/BA-011-coffee.json) — fixture,
не банковский ответ. [Реальный HTTP/браузерный прогон](screenshots/BA-011-verification.json)
проверяет наш API и настоящие Qwen/PostGIS/финансы, а не интеграцию с ВТБ.

protected matching/confirm/version/отсутствие мутаций на настоящем PostgreSQL.
`prek run --all-files`, frontend build и smoke проверяют весь существующий контур.

Реальный regression workflow после запуска Compose/Ollama и импорта OSM:

```powershell
$env:BA010_REAL = '1'
$env:BA010_ARTIFACT_DIR = 'test-results/ba011-regression'
npm --prefix apps/web run test:e2e
Remove-Item Env:BA010_REAL, Env:BA010_ARTIFACT_DIR
```

демо-маркировка/нулевые действующие рекомендации, mobile 390px и проверка ошибок
консоли. Банковский API ВТБ не вызывается. Mock и verified test fixtures не
выдаются за проверку действующих условий. Скриншоты: [desktop](screenshots/BA-011-bank.png),
