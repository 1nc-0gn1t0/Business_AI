# BA-009: финансовые формулы и сценарии

`POST /api/v1/finance/calculate` — самостоятельный read-only инструмент.
Вычисления выполняет `app/finance/engine.py` без LLM, БД, геосервиса или сети.
Контракты — `app/finance/schemas.py`, архитектурное решение —
[ADR-0006](adr/ADR-0006-financial-engine.md). Формулы основаны на §8.2 PROJECT_PLAN.md.
Банковский бизнес-кейс §8.3, кредитные платежи и финансовый frontend здесь не реализуются.

## Входные данные и пересчёт

Полный редактируемый запрос: [BA-009-coffee-input.json](examples/BA-009-coffee-input.json).
На каждом POST передаются все исходные данные; изменение значения и повторный POST
выполняют пересчёт. Сервер не хранит финансовую сессию, не изменяет BusinessProfile,
не создаёт AnalysisRun и не подтверждает диалог. Черновой профиль допустим для
моделирования, но отмечается warning. UUID профиля/беседы не открывают доступ к БД.

- `profile`: существующий BusinessProfile; budget — пользовательский параметр,
  используется только для сравнения со стартовой потребностью. Город/категория
  задают контекст, а не автоматически найденную аренду/выручку.
- `startup`: оборудование, ремонт, депозит, первоначальный запас, регистрационные/
  организационные расходы, прочие затраты и резерв оборотных средств. Все обязательны,
  включая явный ноль при отсутствии статьи; автоматических рыночных значений нет.
- `monthly_fixed_costs`: rent, payroll, utilities, other; суммы за месяц.
- `working_days_per_month`: целое 1…31, одно для сравниваемых сценариев.
- `scenarios.conservative/base/optimistic`: каждый содержит average_check (>0),
  sales_per_day (целое 0…1000000) и variable_cost_ratio (0…<1, максимум 6 знаков).
  Optional полный fixed_costs переопределяет общие расходы только для этого сценария;
  частичное скрытое переопределение не допускается.
- `sensitivity_changes`: 1…6 различных ненулевых относительных изменений, каждое
  >−1 и ≤1, до 4 десятичных. Пример −0.10/+0.10 — математическое возмущение ±10%,
  а не прогноз рыночной динамики. Параметр обязателен, скрытых диапазонов нет.
- `selected_zone`: optional reference с dataset_slug, data_version, candidate_id,
  ranking_fingerprint из BA-008. Финансовый модуль не проверяет эту ссылку и не
  принимает score. Наличие/смена зоны не меняет экономические значения.

Каждая существенная экономическая вводная имеет `{value, source}`:

```json
{
  "value": "80000.00",
  "source": {
    "origin": "synthetic",
    "source_name": "Editable demo assumption; not market data",
    "data_version": "coffee-finance-demo-v1",
    "confidence": "not_applicable",
    "limitations": ["Not a real rent offer or available premises"]
  }
}
```

Используются существующие DataOrigin/Confidence. `user_input` — введённое пользователем,
не автоматически подтверждённый рыночный факт. `synthetic`/`modelled` — допущение;
synthetic требует confidence=not_applicable. `open_data`/`licensed`/`bank_internal`
требуют source_attested=true, observed_at с часовым поясом и evidence_ref.
Это **аттестация источника вызывающей стороной**: сервис проверяет структуру,
но не скачивает договоры, не проверяет лицензию/подлинность и не заявляет собственной
верификации факта. source_name, data_version и непустые limitations обязательны.

Нельзя маркировать демо-аренду как licensed или факт без подтверждающего источника.
Если вводной нет, API возвращает 422 с путём недостающего поля; клиент должен
запросить её или явно передать сценарное допущение. Отсутствующий budget разрешён:
расчёты выполняются, но budget.status=budget_unknown и сравнение=null.

## Арифметика, единицы и округление

Новые денежные значения и доли передавайте **decimal-строками** (либо точными
целыми); float/bool запрещены. Деньги ≥0, максимум 18 значащих разрядов при
максимум 2 дробных. Продажи/дни — строгие JSON integers. BusinessProfile сохраняет
прежний DTO, но его budget также рекомендуется отправлять строкой.

Расчёт использует отдельный Decimal Context, precision=64, ROUND_HALF_UP,
не зависит от глобальных precision/rounding/traps. Binary float в формулах нет.
Результаты денег и вычисленных counts сериализуются decimal-строками, включая
целочисленную безубыточность; это сохраняет точность больших значений для frontend.
Не преобразовывайте их в JS Number для денежных вычислений.

```text
monthly_sales = sales_per_day × working_days
revenue = average_check × monthly_sales
variable_cost = HALF_UP(revenue × variable_cost_ratio, 2)
fixed_cost = rent + payroll + utilities + other
contribution_per_sale_exact = average_check × (1 − variable_cost_ratio)
monthly_contribution = revenue − variable_cost
operating_result = monthly_contribution − fixed_cost
break_even_sales_per_day = ceil(fixed_cost / (contribution_per_sale_exact × working_days))
```

Количество продаж целое, чек и fixed costs имеют копейки, поэтому revenue и
сумма fixed costs точны до копеек. Расход variable_cost округляется **один раз
за месяц**, затем вычитается; сумма строк отчёта сходится до копейки. Это
копеечное представление непрерывной формулы плана: округление затрат может
давать до половины копейки отличия от неокруглённого аналитического результата.
Округлённый contribution_per_sale нужен для отображения, в формулу безубыточности
не подставляется. Положительная маржа меньше копейки не становится нулём:
точное значение сохранено, BE рассчитана, возвращается предупреждение.

Пример границы: чек 1.01, доля 0.5, одна продажа/день и один день дают variable
cost 0.51, contribution 0.50; точная unit margin — 0.505, display — 0.51.
BE использует 0.505. Ноль fixed costs даёт BE=0; ноль продаж допустим и может
давать убыток. Ratio=1, неположительный чек/число дней отклоняются до вычислений.

Стартовая потребность — сумма всех startup-строк, включая резерв. Депозит,
запас и резерв — разные использования денег, **не все являются расходами/CAPEX**.
Расходование стартового запаса не прибавляется повторной строкой к ежемесячным
variable costs: модель учитывает потребление через ratio, но не ведёт движение
запасов/денег. Резерв не уменьшает operating_result и не доказывает будущую ликвидность.

`budget.remaining=profile.budget−total_initial_funding`, gap=max(0,−remaining).
Статусы within_model_budget/model_budget_shortfall относятся к **введённой модели**,
не к реальной цене/доступности помещения. Недостаток денег не порождает фиктивный
кредит. Funding профиля не добавляет условия банка/кредитные расходы автоматически.

## Три сценария и чувствительность

Сценарии целиком заданы пользователем; нет скрытых множителей спроса. Если
результаты не упорядочены согласно именам conservative/base/optimistic, вводные
не переставляются: возвращается warning. Сравнение показывает отличия выручки
и operating_result от base, без процентов вероятности или обещания прибыли.

Чувствительность — one-at-a-time для base: average_check, sales_per_day,
rent, variable_cost_ratio. Остальные вводные фиксируются, каждый раз применяется
тот же расчёт. Деньги округляются до копеек, ratio — 6 знаков, продажи — до целых
HALF_UP. Возвращаются requested relative_change, actual_value, новый результат,
отличие от base и BE. Если возмущение выходит за исходный домен (например ratio≥1,
нулевой округлённый чек или превышение денежного лимита), строка outside_domain
с null результатом; недопустимое значение не зажимается в допустимый интервал.
Совместные шоки, нелинейность спроса/эластичность и вероятность сценариев не моделируются.

Ответ включает полный request_snapshot, resolved inputs каждого сценария,
версию `business-finance-decimal-v1`, SHA256 economic request fingerprint,
исходные sources и формулы. Каждая расчётная метрика — origin=modelled,
с formula_id, input_paths, алгоритмом и единицей. Отдельный FinancialMetric
с Decimal сохраняет денежную точность; существующий float MetricWithProvenance
BA-003 не переписывается. Технические UUID/confirmation_state не влияют на
экономический fingerprint; статус подтверждения всё равно виден в snapshot/warnings.
Числа, fingerprints и весь ответ идентичны при повторном одинаковом запросе.

## Демо: кофейня в Казани, бюджет 2 млн ₽

**Все перечисленные экономические вводные — синтетические редактируемые допущения.**
Это не стоимость аренды/оборудования на рынке Казани и не измеренный спрос.
Бюджет 2000000 — параметр пользовательского сценария. В запросе приложена ссылка
на реальную архивную зону BA-008; финансовые числа из неё не получаются.

Старт: оборудование 700000, ремонт 400000, депозит 160000, запас 100000,
организационные расходы 40000, прочие 100000 = **1500000 ₽**; резерв 300000,
итого **1800000 ₽**, остаток бюджета по модели **200000 ₽**.
Фиксированные/месяц: аренда 80000, зарплаты 180000, коммунальные 20000,
прочие 20000 = **300000 ₽**; 30 рабочих дней.

| Показатель | Консервативный | Базовый | Оптимистичный |
|---|---:|---:|---:|
| Чек, ₽ | 250 | 300 | 350 |
| Продаж/день | 60 | 100 | 130 |
| Доля переменных затрат | 40% | 35% | 32% |
| Выручка/месяц, ₽ | 450000 | 900000 | 1365000 |
| Переменные/месяц, ₽ | 180000 | 315000 | 436800 |
| Маржинальный доход/месяц, ₽ | 270000 | 585000 | 928200 |
| Операционный результат/месяц, ₽ | **−30000** | **285000** | **628200** |
| Безубыточность, продаж/день | **67** | **52** | **43** |

При base ±10% чека/продаж дают ±58500 ₽ operating_result, аренды — ∓8000 ₽,
ratio — ∓31500 ₽. Изменение base до 90 продаж/день даёт 226500 ₽.
Это математические изменения при фиксированных прочих параметрах, не прогноз.


Архив реального HTTP-ответа на **синтетический сценарий**:
[BA-009-coffee-result.json](examples/BA-009-coffee-result.json).
Скрипт сверяет три сценария независимым Fraction/целочисленным эталоном,
проверяет startup/budget, повторяемость, пересчёт и независимость от зоны.

Модель не считает чистую прибыль, денежный поток, окупаемость, налоги,
амортизацию, кредитные выплаты, сезонность и движение оборотного капитала.
Payroll/ratio/other покрывают только явно включённые пользователем расходы;
неучтённые статьи не превращаются в нулевые реальные обязательства.
Нет подтверждённых аренды, доступности помещений, трафика/спроса и выручки.
Положительный результат не подтверждает финансовую реализуемость бизнеса.
