# BA-007: географические зоны-кандидаты

`POST /api/v1/geo/{slug}/candidates` — детерминированный read-only инструмент
FastAPI/PostGIS. Не вызывает LLM, Overpass или платные API. Не меняет диалоги,
подтверждение профиля и геоданные. Новая миграция не нужна.

## Запрос и граница доступа

Тело принимает существующий `BusinessProfile` как **переданный снимок**:
`profile.conversation_id` не используется для чтения приватной беседы. Пример:

```json
{
  "profile": {
    "conversation_id": "00000000-0000-0000-0000-000000000007",
    "city": "Казань",
    "category": "кофейня",
    "budget": "2000000",
    "preferences": {"format": "навынос"}
  },
  "cell_size_m": 500,
  "min_separation_m": 1000,
  "limit": 5
}
```

Для повторения закрепите `data_version` из ответа. Необязательные фильтры:
`search_bbox` (west/south/east/north), `district_ids`, `excluded_district_ids`.
Предпочтительные районы профиля разрешаются по точному имени без учёта регистра,
`ё/е` и лишних пробелов. Несколько районов образуют объединение; явный список ID
пересекается с предпочтениями, исключения вычитаются. Неизвестные/неоднозначные
районы блокируют выдачу. Город сопоставляется с метаданными набора; есть явный
алиас Kazan/Казань, произвольного геокодинга нет.

Проверяемые положительные ограничения:

```json
{
  "category": "highway:bus_stop",
  "max_distance_m": 500,
  "min_count": 1,
  "profile_constraint": "рядом с остановкой"
}
```

Такие объекты передаются в массиве `requirements`. `profile_constraint` при наличии
должен точно ссылаться на одно из `profile.preferences.constraints`. Это явное
структурированное соответствие, заданное вызывающим клиентом, а не семантическая
проверка свободного текста. Клиент должен согласовать такое соответствие с
пользователем; автоматического LLM-преобразования здесь нет. Несвязанные текстовые
ограничения дают `needs_constraints` и пустой результат. Требования вроде
«аренда до 50 тысяч», площади помещения или отсутствия конкурентов по этим данным
не проверяются: нельзя подменять их условием близости к POI.

Бюджет, источник финансирования и формат сохраняются в снимке; они не становятся
фиктивным фильтром доступности аренды. `not_evaluated` явно сообщает об этом.
Город/категория обязательны для генерации; профиль может быть черновиком для
предпросмотра. Вызов не подтверждает профиль и не запускает сохранённый анализ.

## Алгоритм v1

1. Читать один immutable snapshot активного набора по dataset ID. При смене
   запрошенной версии — 409 `geo_dataset_changed`, неизвестном slug — 404.
2. Допустимая территория: bbox покрытия ∩ search_bbox ∩ районы минус исключения.
   Если выбранный район выходит за покрытие, обрезать и сообщить `partial`.
3. Выбрать UTM по центру **bbox набора**, независимо от поискового фильтра.
   Для Казани EPSG:32639, единицы — метры. Поддерживаются широты −80…84 и ширина
   набора ≤3°. Другие экстенты дают 422 `unsupported_metric_extent`.
4. `ST_SquareGrid`, фиксированное начало сетки (0,0) метрической SRS;
   сторона 250…2000 m, по умолчанию 500 m. Обрезать по допустимой территории,
   убрать полоски с итоговой площадью <25% целой ячейки. Это порог геометрии
   зоны, не минимальная площадь помещения.
5. Внутренний отступ 0,02 m защищает от численных артефактов границ. После
   преобразования снова пересечь с исходной WGS84-территорией, оставить только
   валидные непустые MultiPolygon. Представительная точка — `ST_PointOnSurface`,
   гарантированно внутри зоны; это не адрес и не точка входа.
6. В каждой ячейке нужен наблюдаемый POI из отраслевой политики. Для кофейни:
   `amenity:cafe`, `amenity:university`, `amenity:college`, `highway:bus_stop`.
   Ближайший к представительной точке объект внутри ячейки становится evidence,
   с OSM type/ID/version, датой, именем (может быть null) и способом представления.
   Политики для пекарни, ресторана, салона и продуктового магазина — в
   `candidate_policy.py`; неизвестная категория даёт `insufficient_data`.
   Это фильтр наблюдаемого контекста, не гипотеза о прибыльности.
7. Все proximity-условия обязательны одновременно. `ST_DWithin(geography)`
   измеряет метры от представительной точки до известных POI того же snapshot.
   `mapped_count` — число OSM features, не гарантированно уникальных организаций.
   За краем покрытия число может быть неполным; отсутствие объектов ничего не
   доказывает. Дорожных/пешеходных расстояний и отрицательных условий нет.
8. Выбрать до 10 ячеек географическим разнесением: первая ближе к среднему
   положению допустимых представительных точек, последующие максимально удалены
   от уже выбранных. Равенства разрешаются индексами i,j. `min_separation_m`
   проверяется в UTM между точками. Это жадная пространственная выборка,
   не максимизация числа зон и не коммерческий ranking. Может выбрать края
   покрытия; порядок выдачи не означает предпочтение.

Лимит верхней оценки сетки — 12000 ячеек, иначе 422 `candidate_grid_too_large`.
Нет скрытого усечения пула до выбора. Используются существующие GiST/GIN,
параметризованный SQL и statement_timeout 5 s; сбой БД/таймаут даёт существующий
санитизированный 503. Большой регион следует сузить или увеличить шаг сетки.

## Ответ и воспроизведение

Типизированный `CandidateCollection` — GeoJSON FeatureCollection. Полигон:
`MultiPolygon`, EPSG:4326, координаты **longitude, latitude**; площадь `area_m2`
рассчитана в `metric_srid`. Представительная точка и OSM anchor — отдельные
GeoJSON Point/Feature. `origin=modelled`, `is_actual_listing=false`,
`kind=geographic_zone_not_premises`; исходный dataset — `origin=open_data`, ODbL.

Ответ фиксирует `profile_snapshot`, полный `request_snapshot` с фактической
версией данных, `algorithm_version=utm-grid-dispersion-v1`,
`policy_version=osm-anchor-policy-v1`, SHA256 `request_fingerprint`, версии
PostGIS/GEOS/PROJ (`spatial_runtime`) и `eligible_count`. ID = SHA256 от
fingerprint и индексов ячейки. Технические UUID профиля/беседы и состояние
подтверждения не влияют на генерацию/ID; бюджет нормализуется как decimal.
Изменение геометрии/политик требует новой версии алгоритма/политики.
Идентичные параметры, snapshot и GIS runtime дают те же ID и геометрии;
`dataset.age_days/stale` зависит от текущей даты. API работает с активной версией:
после обновления старый pin даёт 409; исторические snapshots остаются в БД.

Статусы 200: `ok`, `partial` (обрезка/меньше запрошенного числа),
`no_candidates`, `insufficient_data`, `needs_constraints`. Все содержат
машиночитаемые `reasons`, версии и ограничения. Пустой результат не означает
отсутствия подходящих мест в действительности. `coverage=saved_bbox_only`
сохраняется даже при `ok`: это успех внутри покрытия, не полнота всего города.

Результаты не сохраняются как новый AnalysisRun и не читают сохранённый профиль:
инструмент готов для будущей оркестрации с явным снимком подтверждённого профиля.
Существующие API/optimistic locking диалогов не менялись. Карта, ranking/scoring,
финансовые расчёты и автоматический вызов из чата в BA-007 не реализуются.

## Проверка на реальных данных

```powershell
docker compose up --build --detach --wait
uv run --locked --project apps/api python scripts/eval_candidate_zones.py --output local-candidate-eval.json
# Можно проверить тот же API через nginx:
uv run --locked --project apps/api python scripts/eval_candidate_zones.py --api http://127.0.0.1:5173 --output local-candidate-proxy-eval.json
```

Скрипт read-only, требует импорт `kazan-centre` по GEO_DATA.md, не скачивает данные.

Наличие кафе/остановки — проверяемое основание включить ячейку в пул, а не
доказательство спроса. Зоны ~15–25 гектаров; внутри возможны вода, дороги,
промышленные/недоступные территории. Нет слоёв землепользования, свободных
помещений, аренды, измеренного трафика и доходности. Поиск участка/помещения
требует дополнительных данных и проверки на месте. BA-008 должна отдельно
рассчитывать факторы/ранжирование с учётом отсутствующих данных.
