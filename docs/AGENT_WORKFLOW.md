# Business AI — протокол ротации разработчиков и AI-агентов

**Цель:** любой Codex/Claude/разработчик продолжает проект без потери контекста и без повтора проделанной работы. Используется вместе с `PROJECT_CONTEXT.md`, `PROJECT_PLAN.md` и `HANDOFF.md`.

## A. На входе (первые 2–5 минут)

1. Обнови локальную ветку (`git fetch`, `git pull --ff-only` там, где это безопасно). **Никогда не делай reset/force push чужой работы без согласования.**
2. Прочитай короткий `README`, `docs/PROJECT_CONTEXT.md` и `docs/HANDOFF.md`; затем релевантные разделы канонического `docs/PROJECT_PLAN.md` для текущей задачи. Не загружай весь план в контекст без необходимости.
3. Проверь `git status --short`, текущую ветку, последний коммит и реальные тесты. Не верь слепо HANDOFF.
4. Назови одну основную задачу, список файлов, ожидаемый критерий приёмки. Если есть блокер — сообщи до изменения архитектуры.

## B. Во время разработки

- Работай **одной законченной вертикальной задачей**, а не расползайся по всему стеку.
- Изменения в пределах архитектуры; новые библиотеки — с обоснованием и минимальными правами.
- Для расчётов и провайдеров сначала тесты и схемы, потом реализация.
- Держи код, документы, команды запуска актуальными.
- Не добавляй реальные личные/банковские данные, секреты, коммерческие выгрузки с неизвестной лицензией.
- Синтетические данные никогда не называй реальными. Банк **не** одобряет кредит через нашу LLM.
- Если лимит токенов близок, **остановись раньше**, обнови HANDOFF и push. Не начинай задачу, на которую оставшихся токенов заведомо не хватит.

## C. Передача работы

1. Выполни доступные линтеры, типизацию, тесты и сборку; запиши **точные команды и исход**.
2. Убедись, что `.env`, API-ключи, cookies и личные данные не в diff.
3. Обнови `docs/HANDOFF.md` **конкретно**: что сделано, что не сделано, на чём остановился, файлы/тесты, блокеры, первые 1–3 шага дальше.
4. Коммит в feature-ветку; push; в HANDOFF укажи `branch` и `commit SHA`. Если SHA меняется из-за коммита самого HANDOFF, в итоговом сообщении укажи **фактический HEAD** — это не повод переписывать историю ради само-ссылки.
5. По готовности задачи — PR/merge в `main` после проверки, но не считать её сданной до подтверждённого push.

## D. Формат минимального статуса после сеанса

```text
Task: BA-...
Done: 2–5 фактов, без общей истории
Files: конкретные пути
Tests: команда → PASS/FAIL (с причиной)
Branch/commit: ...
Blockers: ...
Next: одно ясное действие + критерий готовности
```

**Важно:** HANDOFF — не копия чата и не лог с тысячами строк. Он должен умещаться в короткое чтение следующего агента.

## E. Промпт нового агента (можно копировать)

```text
Ты следующий разработчик проекта Business AI (Sab0tage).
В репозитории есть docs/PROJECT_CONTEXT.md (краткая неизменная идея),
docs/PROJECT_PLAN.md (полная согласованная спецификация),
docs/HANDOFF.md (последнее состояние) и docs/AGENT_WORKFLOW.md (порядок работы).
Сначала изучи эти файлы и реальный код/Git. Исполняй следующий конкретный шаг из HANDOFF.
Не меняй продуктовую задумку без отдельного ADR и согласования.
LLM только организует вызовы проверяемых инструментов; синтетические данные всегда помечены;
скоринг по тексту запрещён, реальных банковских интеграций без доступа нет.
Сначала обеспечь работоспособность, затем расширяй фичи.
К концу сеанса прогони проверки, обнови HANDOFF, сделай commit и push.
Если push не удался — прямо скажи об этом. При ограничении токенов передай состояние заранее.
```

## F. GitHub Issue / PR template (минимальный)

**Issue:** `BA-XXX: название`, контекст, входные данные, затронутые модули, критерии приёмки, риски и зависимости.

**PR:** что менялось, ссылки на Issue/ADR, команды тестирования и результат, миграции/лицензии/данные, эффект на UI/API, обновлён ли HANDOFF.

## G. Минимальный стандарт коммитов

Примеры: `feat(geo): BA-006 import city OSM`, `test(finance): BA-009 cover break-even`, `docs: update handoff for BA-001`.

Если несколько людей пишут параллельно, работать в отдельных ветках и выполнять review перед merge. Обновлять один `HANDOFF.md` следует только после согласования владельца интеграционного шага, иначе будет конфликт.
