# ADR-0006: самостоятельное Decimal финансовое ядро

Дата: 23.10.2026, BA-009. Сохраняет модульный монолит и существующие DTO/геомодули.

Выбран чистый Python-сервис с типизированным POST /api/v1/finance/calculate.
Все существенные вводные имеют sources; недостающие расходы не заполняются
фиктивными defaults. Три сценария передаются явно; source attestation для фактов
не означает независимую проверку договоров сервисом. Демо — только synthetic,
бюджет — user_input, результаты — modelled. Денежный FinancialMetric использует
Decimal; float MetricWithProvenance BA-003 остаётся совместимым.

Отдельный Decimal Context precision=64, HALF_UP и ограниченный домен защищают
от binary float/внешнего context. Месячные variable costs округляются один раз
до копеек перед вычитанием, чтобы строки сходились. BE рассчитывается ceil по
неокруглённой unit margin; положительный доход меньше копейки не становится нулём.
Новые money/ratio inputs и вычисленные значения сериализуются decimal strings.

Сравниваем бюджет с суммой начальных использований денег и резерва; депозит,
запас, CAPEX и расходы не приравниваются. Operating result — упрощённый результат
до неучтённых статей, не net profit/cash flow. Отдельно считаются one-at-a-time
возмущения base. Выход за домен возвращает null/outside_domain, без скрытого clamp.

Геозона — только непроверенная context reference; score не преобразуется в спрос
или аренду. Нет сетевых обращений, LLM, миграций, сохранения сессии/AnalysisRun
или подтверждения профиля. Будущий frontend редактирует snapshot и повторяет POST.

Альтернативы: float теряет денежную точность; LLM-арифметика невоспроизводима;
авто-«рыночные» defaults скрывают отсутствие источников; расчёт точной окупаемости
без cash-flow schedule смешивает операционный результат с движением денег.
Расширенная модель налогов/кредита/ликвидности требует явных дополнительных вводных.
