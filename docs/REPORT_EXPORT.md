# Аналитический отчёт BA-015: PDF и JSON

Экспорт выполняется внутри существующего FastAPI-монолита. Он не создаёт банковскую
заявку, не вызывает банковские API и не использует LLM для фактов или резюме.

## Поток и единый снимок

1. Пользователь подтверждает профиль и выполняет геоанализ и/или финансовый расчёт.
2. UI передаёт исходные DTO запросов и fingerprints полученных результатов.
3. Сервер проверяет гостевой доступ, assistant consent, версию/подтверждение профиля,
   принадлежность всех profile snapshots и выбранной зоны. Пересчитывает существующими
   BA-008/009/011/013/014 сервисами и сверяет fingerprints. Самодельные итоговые цифры,
   PDF, картинки и summary от клиента не принимаются.
4. Фиксируется ReportSnapshot business-ai-report-v1: UUID, UTC created_at,
   версия/дата/подтверждённые параметры профиля, результаты и версии источников/алгоритмов.
5. PDF и канонический JSON формируются из этого объекта. 0008_analytical_reports хранит
   JSONB snapshot, его SHA256, готовые PDF bytes и SHA256 PDF, owner conversation и дату.
   Впоследствии скачивание не пересчитывает бизнес-данные и не обращается в интернет.

BusinessProfile vN проверяется под существующей блокировкой строки беседы; изменение
профиля не может вклиниться между проверкой версии и фиксацией снимка. Импорт OSM
сохраняет прежнюю политику BA-006: preparation со старой active data_version →409,
а не незаметная замена набора. Провайдерские версии выбираются явно.

Каждая явная повторная preparation создаёт новый документ. Старый снимок не меняется.
Это не идемпотентная отправка банковской заявки и не фиктивная банковская квитанция.

## Содержание

- Проект: город, тип бизнеса, бюджет, формат, финансирование, районы/ограничения,
  версия подтверждённого BusinessProfile, дата формирования.
- Локации: до 5 реальных зон, выбранная зона, исходные показатели, баллы/составляющие,
  объяснения и ограничения, OSM snapshot/version/license/date, версия политики.
- Схема зон: векторные геометрии из результата сервиса, точки/выбор/атрибуция OSM.
  Без растровых тайлов, платных карт и сетевых изображений. EPSG:4326, приближённая
  локальная проекция для схемы, не навигационная карта и не объявление о помещениях.
- Пешеходный анализ: если рассчитан, точка/расстояние/привязка, сетевые и прямые counts,
  граф/manifest/алгоритм и ограничения. Это может быть отдельная ручная точка, не
  автоматически вход в выбранную зону. В PDF показаны 8 крупнейших категорий;
  полный перечень, линии и POI доступны в JSON. Нет автоматической подмены BA-008
  сетевым рейтингом: отчёт экспортирует baseline рейтинг и отдельно BA-013 catchment.
- Финансы: капитал/бюджет, 3 сценария, расходы/выручка/маржинальный доход/операционный
  результат/безубыточность, сравнение/чувствительность, все вводные/источники и формулы.
- Банк: подходящие и требующие уточнений продукты, основания, неизвестные условия,
  ссылки/даты/ограничения каталога. Демонстрационный статус, credit_decision=not_assessed.
- Дополнительные источники: только явно просмотренный пользователем ProviderResult.
  В UI пока выбран один набор; API позволяет до 3 явно указанных результатов.
- Резюме: детерминированный текст из фактических статусов и отсутствующих данных.
  Нет доходности из OSM-score, выдуманного трафика, стоимости помещения или одобрения.

Полный отчёт не обязателен для частичной аналитики. Нужен хотя бы geo или finance;
пропуски перечислены в missing_sections, в PDF и в UI. Неполный catchment/нет графа
не превращаются в нули или доказательство недоступности.

## Provenance и деньги

Используются существующие DTO, DataOrigin/MetricWithProvenance/InputSource.
Каждый раздел содержит источники либо наследует их по явно указанному пути:

- P: profile = user_input, источник confirmed BusinessProfile, версия profile_version,
  дата profile_updated_at. Подтверждение пользователем не означает независимую проверку.
- G: raw geo наследует evaluation.provenance/dataset (open_data). Геометрии и scores
  modelled. Counts = нанесённые OSM features; расстояния BA-008 по прямой.
- W: catchment = modelled, исходный OSM manifest/graph; соединители модельные.
- F: financial metric = modelled, формула/formula_id/input_paths ссылаются на полный
  FinanceRequest. Каждый input сохраняет источник/версию/ограничения. Если у допущения
  нет даты генерации, в PDF указана дата фиксации отчётом, не дата рыночного наблюдения.
- B: источник каталога, verification/reviewed_at/unknown_conditions, не решение банка.
- D: ProviderResult сохраняется полностью с measurement origin/date/unit/version,
  dataset license/geography/quality/limitations. Synthetic не превращается в open_data.

JSON включает provenance_rules и metric_units для однозначной интерпретации путей.
В PDF синтетические вводные помечены в предупреждениях и каждой строке таблиц.
Провайдерская синтетическая аренда **90000** не подставляется в финансовые вводные
примера **100000**: это разные явные сценарные источники. Денежные значения
сохраняются Decimal strings BA-009; float используется только для масштаба графика,
не для финансовых вычислений. Операционный результат не net profit/cash flow.

## API и доступ

Все маршруты ниже требуют `X-Conversation-Token` соответствующей беседы.
Токен не помещается в URL/JSON/PDF/filename. Полная история чата, LeadDraft,
контакты для банковской заявки и секреты не включаются. Технические UUID профиля/
беседы сохраняются для согласованности existing DTO; сами по себе доступ не дают.

- POST `/api/v1/conversations/{conversation_id}/reports` →201 ReportView.
- GET `…/reports/{report_id}` →метаданные, SHA, размеры, current/outdated и причины.
- GET `…/reports/{report_id}/snapshot` →типизированный ReportSnapshot для интеграций.
- GET `…/reports/{report_id}/file?format=pdf|json` →attachment нужного Content-Type.

Пример структуры preparation (полные вложенные DTO берутся из результатов сервисов):

```json
{
  "expected_version": 3,
  "geo": {"dataset": "kazan-centre", "request": {"candidates": {}, "scoring": {}}, "fingerprint": "<SHA>"},
  "selected_zone": "<candidate_id>",
  "finance": {"request": "<FinanceRequest DTO>", "fingerprint": "<SHA>"},
  "bank": {"request": "<MatchRequest DTO>", "fingerprint": "<SHA>"},
  "walking": {"dataset": "kazan-centre", "request": "<CatchmentRequest DTO>", "fingerprint": "<SHA>"},
  "providers": [{"request": "<IndicatorQuery DTO>", "fingerprint": "<SHA>"}]
}
```

Выше схема, не готовый HTTP-payload. Точный контракт - OpenAPI `/docs` и schemas.py;
готовый проверенный выход - examples/BA-015-kazan-coffee.json.

Content-Disposition использует только ASCII/UUID. Content-Type application/pdf либо
application/json; Cache-Control private,no-store; nosniff; X-Report-Snapshot-SHA256
одинаков для обоих файлов. Некорректный UUID/format →422, чужой ID/ключ →404,
отсутствующий ключ →401. Экспорт не требует marketing/demo_lead consent.
Создание требует действующее assistant consent; чтение уже созданного снимка -
авторизация владельца, без нового бизнес-расчёта и без согласия на банковскую передачу.

## Актуальность и воспроизводимость

Канонический JSON: UTF-8, sort_keys, фиксированные separators, без NaN.
PDF ReportLab с invariant canvas и встроенным DejaVu Sans (лицензия рядом со шрифтом).
При фиксированном ReportSnapshot и версиях renderer/ReportLab/font JSON и PDF
детерминированы; готовые PDF bytes дополнительно хранятся в БД. Две preparation
различаются UUID/created_at и служебными датами/таймингами пересчётов. PDF metadata
CreationDate фиксирована ReportLab на 2000-01-01 ради воспроизводимости; фактическая
дата отчёта напечатана в документе и JSON. Смена renderer требует новой версии.

При чтении проверяются схема и SHA обоих файлов. Профиль, active OSM/graph/provider,
гео/финансовая/сетевая версия и банковский каталог/as_of проверяются на актуальность.
Исторические source timestamps сохранены, источники не перезаписываются.
UI немедленно блокирует прежний документ при редактировании вводных/выбора/режима;
смена поисковых весов также очищает устаревший анализ. Перед скачиванием проверяется
серверный статус. Вводные финансового frontend локальны: сервер не узнаёт о
несохранённом редактировании вне UI, поэтому snapshot всегда обозначен как снимок,
а не «последние вводные пользователя» во всех возможных клиентах.

409 report_outdated блокирует обычное скачивание. Владельцу доступен явный
`historical=true` для старого снимка (status outdated сохраняется в HTTP header),
UI автоматический обход не делает. При DATA_DEMO_ENABLED=false документ с данными
SyntheticProvider не скачивается даже через historical=true; история не удаляется.

## Ограничения ресурсов и проверки

ASGI limiter отклоняет body >128 KiB до JSON-декодирования. До 5 зон/1 catchment/
3 provider запросов. Snapshot <=4 MiB, PDF <=3 MiB/40 страниц, до 20 документов на
беседу. Проверки времени между расчётами:20с, после PDF:30с; это не принудительное
прерывание произвольной Python-инструкции. SQL имеет существующий timeout 5с.
Большие результаты/неподходящая вёрстка возвращают понятные 413/422/503, без частичного
сохранения. Для публичного пилота нужны глобальные квоты, retention/удаление и
нагрузочные проверки; новая очередь/микросервис в BA-015 не добавлены.

Unit: сериализация/нет секретов/PDF structure/кириллица/₽/детерминированность.
PostgreSQL/API: общий снимок, финансовая сверка, доступ/изоляция, stale profile,
изменённые вводные, повреждение, partial/size, geo/bank versions, synthetic/disable.
Frontend: запрос из DTO, скачивание с токеном только в header, invalidation/errors.
CI без GPU/весов/платных API. Настоящий e2e включает Qwen, PostGIS, walking,
finance, catalogue, SyntheticProvider, загрузку PDF/JSON и проверку stale inputs.
Требования к реальному запуску - USER_INTERFACE/DATA_PROVIDERS. Команда:

```powershell
$env:BA010_REAL='1'
$env:BA010_ARTIFACT_DIR='test-results/ba015-regression'
npm --prefix apps/web run test:e2e
```

Последний результат и оставшиеся ограничения - HANDOFF.md. PDF-пример содержит
12 страниц; все отрендерены Poppler и просмотрены, отдельно проверены таблицы,
кириллица/₽/маркировка синтетики. Промежуточные PNG остаются в игнорируемом tmp/pdfs.
